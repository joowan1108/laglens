LagLens: Seeing What a Robot Actually Executes When Its Policy Thinks Too Slowly

A visual analytics tool for action-chunk execution under inference latency (sync vs. asynchronous inference, open-loop execution horizon)

Modern robot policies (Diffusion Policy, ACT, π0, SmolVLA) predict a chunk of future actions and execute part of it open-loop. Inference takes time d, so the robot either waits (sync) or keeps executing the old chunk and switches when the new one arrives (async).
  • Stale actions: under async inference an action executed at time τ was planned from the observation at τ−d (VLASH, 2025).
  • Seams: where chunk k+1 replaces chunk k, the plans can disagree → jumps, mode switches (BID 2025; SEAM 2026).
  • Tuning by hand: strategy, latency budget and execution horizon are chosen from aggregate success-vs-delay curves (RTC 2025; LeRobot async docs).
  • Gap: today's views are debug plots and tables. We found no visual analytics work on chunk execution or async inference (IEEE VIS / EuroVis / CHI search).
Our idea: paired counterfactual replay. We run one pretrained policy from the same {{N_SEEDS}} initial states under {{N_SCHED}} execution schedules and log every predicted chunk. Analysts can then ask: “Which episodes flip from success to failure when I go async with 400 ms latency, and is it the stale actions or the seams that cause it?”

Dataset type: multidimensional table of episodes, each linked to two temporal tables and to a spatial field (512 × 512 px workspace).
  • Step table ({{N_STEPS}} items) · keys: schedule, seed, t (ordinal, 10 Hz) · values: agent x, y; block x, y (interval, px); block θ (cyclic, rad); action x, y (interval, px); chunk id (ordinal); index j 0–15 (ordinal); age (ratio, steps); held (binary); coverage (ratio 0–1).
  • Chunk table ({{N_CHUNKS}} items) · keys: schedule, seed, chunk id · values: t_obs, t_avail (ordinal time), executed window, 16 predicted (x, y) actions.
  • Size: {{CSV_KB}} KB episode CSV + {{DETAIL_MB}} MB step/chunk JSON (lazy-loaded per schedule).
Keys vs. values: keys = (strategy, latency, horizon, replicate) → schedule; × seed → episode; × t → step; × chunk id → chunk. Everything else is a value.
Novel data: no public dataset logs per-inference chunks (survey, Oct 2026). Generated by us; scripts in scripts/. 1 step = 100 ms.
Model: Chi et al., Diffusion Policy (2023), checkpoint by Hugging Face LeRobot · PushT env: gym-pusht2 / 7

3 · Why — Task Abstraction (action + target, Munzner)

Four tasks, from schedules down to a single seam

#Action + targetConcrete question (Mara)WhyExpected outcome
T1Compare → trends of success / seam gap / staleness across schedules “How fast does success fall with latency for each strategy, and which horizon is most robust?” Choose a candidate schedule for the latency the lab actually has. A shortlist of robust schedules and a latency budget per strategy.
T2Locate → outliers: initial states whose outcome flips between a reference and a candidate schedule “Going from sync d=0 to naive async d=4, which seeds start failing, and which are rescued?” Aggregate rates hide which situations break; paired seeds isolate the schedule's effect. A small set of fragile seeds to inspect (and to add to a regression test set).
T3Identify → features in time & space: where stale actions, seams and idling occur in a flipped episode “At which step does the candidate diverge from the reference, and was the executed action stale, a seam jump, or a wait?” Diagnose the mechanism of failure, not just its rate. A causal hypothesis, e.g. “a 30 px seam right at block contact makes the push slip.”
T4Discover → correlation between seam gaps (plan inconsistency) and task outcome (coverage) over paired episodes “When a seed moves from R to C, do larger seams go with lower coverage? Does inpainting shrink the seams?” Recent work claims failed episodes show larger chunk-boundary artifacts (Wang 2026); check it on our policy. Evidence for or against a strategy (direction and size of shift per seed).
Arjun mainly needs T1 (latency budget) and T2 (is the drop driven by a few seeds?). Mara chains T1 → T2 → T3 → T4 in one session: overview first, then drill down to a single chunk hand-over (details on demand).

Why this is not a Tableau dashboard: the views are driven by a reference/candidate pair of schedules and by chunk provenance (each executed action is linked to the observation and the chunk it came from). The fan, the seam ticks and the paired flip colouring are computed from the logged predictions, and selections propagate across all five views.
